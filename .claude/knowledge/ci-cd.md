# CI/CD Pipeline

## Overview
GitHub Actions workflow that automatically builds and deploys the ASP.NET Core backend to Azure App Service on every push to `develop` that touches `backend/**`. Manually triggerable via `workflow_dispatch`.

## Location
- `.github/workflows/develop_bank-operations-api.yml` — the only workflow file; handles both build and deploy

## How it works
1. Trigger fires on push to `develop` with path filter `backend/**` (or manual dispatch)
2. **Build job** runs on `ubuntu-latest`:
   - Checks out the repo
   - Sets up .NET 10 (`dotnet-version: '10.x'`)
   - `dotnet build --configuration Release` from `backend/BankOperations`
   - `dotnet publish -c Release -o $DOTNET_ROOT/myapp` from `backend/BankOperations`
   - Uploads the published output as artifact `net-app`
3. **Deploy job** runs on `ubuntu-latest`, depends on build job (`needs: build`):
   - Downloads artifact `net-app`
   - Logs in to Azure via OIDC Federated Identity (`azure/login@v2`)
   - Deploys to Azure Web App `bank-operations-api`, Production slot (`azure/webapps-deploy@v3`)

## Key details
- **OIDC auth — no client secret.** The deploy job uses `id-token: write` permission and three GitHub secrets to authenticate. There is no long-lived credential to rotate or leak.
- **Secrets are named with hash suffixes** (e.g. `AZUREAPPSERVICE_CLIENTID_B42924C8D70546FFACB2FF5F5F31783E`) — these were generated by the Azure portal integration and must not be renamed without updating the workflow.
- **Path filter `backend/**`** — pushing only to `frontend/`, docs, or config files will NOT trigger a deployment. If the filter needs to be removed (e.g. to test the pipeline), add a second `paths` entry or use `workflow_dispatch`.
- **`working-directory: backend/BankOperations`** is set on both the build and publish steps — the project file is not at the repo root.
- **`id-token: write` is on the deploy job only**, not the build job — minimal permissions per job.
- The artifact path `${{env.DOTNET_ROOT}}/myapp` is an Ubuntu environment variable set automatically by `actions/setup-dotnet`.
- App name on Azure is `bank-operations-api`, slot is `Production`.

## Code snippets

### Trigger
```yaml
on:
  push:
    branches:
      - develop
    paths:
      - 'backend/**'
  workflow_dispatch:
```

### Build job
```yaml
- name: Set up .NET Core
  uses: actions/setup-dotnet@v4
  with:
    dotnet-version: '10.x'

- name: Build with dotnet
  run: dotnet build --configuration Release
  working-directory: backend/BankOperations

- name: dotnet publish
  run: dotnet publish -c Release -o ${{env.DOTNET_ROOT}}/myapp
  working-directory: backend/BankOperations

- name: Upload artifact for deployment job
  uses: actions/upload-artifact@v4
  with:
    name: .net-app
    path: ${{env.DOTNET_ROOT}}/myapp
```

### Deploy job (OIDC login + deploy)
```yaml
permissions:
  id-token: write
  contents: read

- name: Login to Azure
  uses: azure/login@v2
  with:
    client-id: ${{ secrets.AZUREAPPSERVICE_CLIENTID_... }}
    tenant-id: ${{ secrets.AZUREAPPSERVICE_TENANTID_... }}
    subscription-id: ${{ secrets.AZUREAPPSERVICE_SUBSCRIPTIONID_... }}

- name: Deploy to Azure Web App
  uses: azure/webapps-deploy@v3
  with:
    app-name: 'bank-operations-api'
    slot-name: 'Production'
    package: .
```

## Dependencies
- `actions/checkout@v4` — repo checkout
- `actions/setup-dotnet@v4` — installs .NET 10 on the runner
- `actions/upload-artifact@v4` / `actions/download-artifact@v4` — artifact hand-off between jobs
- `azure/login@v2` — OIDC login to Azure
- `azure/webapps-deploy@v3` — deploys the published output to Azure App Service

## How to extend

### Add a test step
Insert between build and publish in the build job:
```yaml
- name: Run tests
  run: dotnet test --configuration Release --no-build
  working-directory: backend/BankOperations
```

### Trigger on frontend changes too
Add a second path entry under `paths:`:
```yaml
paths:
  - 'backend/**'
  - 'frontend/**'
```
Note: this would require a separate deploy job for the frontend (e.g. Azure Static Web Apps).

### Add a staging slot
Duplicate the deploy job, change `slot-name` to `'Staging'`, and add a manual approval gate between staging and production using GitHub Environments.
